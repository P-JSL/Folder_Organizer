# Windows 파일 복사·이동 메타데이터 문제 분석 및 수정

분석일: 2026-11-17(KST). 기준 소스: `6a42a74b52e2902b2b46e933f8fd9f152719570f`.
대상은 Python판의 실제 파일 작업 코드이며, 버전·의존성·릴리즈는 변경하지 않았습니다.

## 확인한 문제

Python판은 파일의 주 데이터 스트림만 읽고 쓰는 `_copy_verified()`로 복사·이동을
수행합니다. 검증도 크기·파일 ID·수정 시각·주 데이터의 SHA-256을 기준으로 합니다.
이 정보만으로는 NTFS의 추가 데이터 스트림(ADS)과 EFS 암호화 속성 보존을 증명할 수 없습니다.

반면 이미 존재하는 복구 데이터 압축 보호와 Rust판의 복사·이동 경로에는
추가 스트림·EFS·스트림 조회 실패를 거부하는 보호가 있습니다. Python판의
복사·이동 경로가 같은 보호를 사용하지 않는 것이 이번에 확인한 불일치입니다.

| 조건 | 수정 전 동작 | 영향 |
| --- | --- | --- |
| 이름 있는 ADS 또는 빈 ADS가 있는 파일 | 미리보기에서 일반 복사·이동 계획을 허용 | 대상 파일에 추가 스트림이 표현되지 않음 |
| 미리보기 후 ADS를 추가하고 주 데이터 수정 시각을 원복 | 주 데이터 검증에 통과해 이동을 완료로 표시 | 주 데이터가 같아도 완전한 복사본이라는 보장이 없음 |
| 복사 도중 ADS 추가 | 추가 스트림을 확인하지 않고 복사를 완료 | 원본과 대상의 보존 정보가 달라질 수 있음 |
| 원본을 보관 경로로 옮기는 순간 ADS 추가 | 완료로 표시하고 원래 경로를 비움 | 새 메타데이터가 있는 전체 파일이 사용자 경로에서 사라짐 |
| EFS 암호화 또는 스트림 조회 실패 | 해당 보호가 복사 경로에 없음 | 암호화 보존을 보장할 수 없거나 보존 불가능 여부를 놓침 |

기존 이동은 원본을 비공개 `original_backup`에 보관하므로, 모든 경우를
영구 데이터 손실이라고 단정하지 않습니다. 다만 사용자에게 보이는 대상 파일이
원본 전체를 표현하지 못하면서 성공으로 표시되는 문제입니다. EFS 입력은 일반
바이트로 읽히므로, 대상의 암호화 보존을 확인하지 않고 복사해서도 안 됩니다.
EFS의 이 경로는 소스와 속성 응답 모사로 확인했으며 실제 EFS 파일 시험은 하지 않았습니다.

## 수정 내용과 근거

`folder_organizer/operations.py`에 `_require_primary_stream_copy()`를 추가했습니다.
기존 `recovery_payload.compaction_preflight()`의 읽기 전용 Windows 속성·스트림
조회 보호를 재사용하고, 보존할 수 없는 속성 또는 불완전한 조회는
`OperationError`로 처리합니다. 압축·청크 생성·실제 파일 변경을 호출하는 것은 아닙니다.

1. 일반 복사·이동·날짜/확장자 정리·규칙 분류 미리보기에서 지원하지 않는 파일을 거부합니다.
2. 실행 시 대상 파일을 만들기 전 다시 확인합니다. 미리보기 후 생긴 스트림도 거부합니다.
3. 복사와 바이트 검증을 마친 후 다시 확인합니다. 실패하면 기존 보호 경로로 부분 복사본을 숨겨 보존하며 원본은 유지합니다.
4. 이동의 원본 보관 직전과 실제 보관 파일을 검증한 뒤에도 확인합니다. 이 사이 추가된 ADS를 발견하면 전체 파일을 원래 경로로 되돌리고, 경합으로 되돌릴 수 없으면 기존 저널의 복구 경로에 보존합니다.

`_retain_verified()`의 새 `primary_stream_only` 옵션은 일반 이동의 원본 보관에만
적용합니다. 파일 전체를 같은 볼륨에서 이름 변경하는 `delete_files` 보관·복원과
기존 전체 파일 보관 경로에 이 제약을 일괄 적용하지 않습니다.

추가 스트림을 복사하는 새로운 포맷이나 암호화 우회는 도입하지 않았습니다.
조회가 불완전한 네트워크/파일시스템 제공자는 복사·이동이 거부될 수 있습니다.
기존의 주 데이터만으로 불완전하게 복원될 수 있는 기록도 새 복사 보호에 따라
실패로 남을 수 있으며, 기존 전체 원본 보관본을 조용히 지우지 않습니다.

전체 앱의 기존 통과 검사·빌드·화면 캡처는 반복하지 않았습니다.

`C:`의 NTFS에 만든 고유 임시 폴더에서 검사했습니다. 원본 주 데이터·빈 스트림·

## 검증의 한계와 남은 상태

- 설치된 Windows의 원격 세션은 연결 재설정으로 사용할 수 없었습니다. 전체 데스크톱 GUI나 배포 EXE를 실행해 통과했다고 표시하지 않습니다.
- Windows PE에서도 실제 Win32 스트림 API와 NTFS를 사용했지만, 완전한 Windows 사용자 세션·NAS·EFS 서비스 동작을 대신하지는 않습니다.
- 실제 EFS 파일, 실제 스트림 조회 권한 거부/미지원 제공자는 시험하지 않았습니다. 해당 거부 경로는 속성·오류 응답 모사로 확인했습니다.
- Rust판에는 이미 같은 종류의 보호가 있어 수정하지 않았고, Rust 검사도 재실행하지 않았습니다. 두 판의 모든 기능이 동등하다는 주장은 하지 않습니다.
- 기존 설치를 다시 적용하거나 레지스트리 복구를 반복하지 않았습니다. 검사 데이터는 새 임시 폴더에만 생성했고, 공개 게시·푸시·새 릴리즈는 수행하지 않았습니다.

변경을 원복하려면 `operations.py`의 이번 변경과 새 검사·분석 파일만 대상으로
되돌립니다. VM 디스크·기존 저널·사용자 원본 파일을 지우는 작업은 필요하지 않습니다.
