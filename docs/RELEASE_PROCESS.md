# Windows 빌드와 릴리스

## v0.6.0 이후 · Python과 Rust 정식 빌드

사용자가 정식 빌드·릴리스를 지시하면 `Python and Rust release builds` (`dual-release.yml`)를 고정된 소스에서 수동 실행합니다. 시험용 빌드 워크플로를 거치지 않습니다. Python과 Rust 실행 파일·도우미를 각각 만들고, 새 Windows 경로와 두 배포 파일의 계약만 확인합니다. 기존 통과 검사는 반복하지 않으며, 실패 수정 후에는 실패한 검사·새 회귀 사례와 아직 실행하지 못한 항목만 수행합니다.

두 ZIP은 `FolderOrganizer-Python-Windows-x64`, `FolderOrganizer-Rust-Windows-x64` 아티팩트로 각각 업로드됩니다. 모든 새 검증이 끝나면 공개 전 릴리스 초안에 두 ZIP과 공통 `SHA256SUMS.txt`를 준비합니다. 새로 받은 파일의 체크섬과 정확한 소스 커밋을 확인한 뒤 해당 커밋의 변경 불가능한 버전 태그를 만들고, 초안을 정식 최신 릴리스로 공개합니다. 초안은 사용자 승인 요청이나 시험판이 아니라 미완성 자산을 자동 업데이트에서 노출하지 않기 위한 배포 단계입니다.

Rust의 Windows 타깃은 MSVC C 런타임 정적 연결을 사용합니다. 앱 식별자·실행 폴더·업데이트 ZIP·복원 기록은 Python판과 구분합니다. 구 단일 Python 태그 워크플로는 v0.0~v0.5 계열로 제한하며, 새 릴리스에서 과거 전체 검사를 자동 반복하지 않습니다.

## v0.5 계열의 기존 절차

먼저 `main`의 Windows·Linux 검사를 통과한 커밋에서 **Windows release → Run workflow**로 검토용 빌드를 만듭니다. 수동 실행은 릴리스를 게시하지 않습니다. 완료된 작업의 `FolderOrganizer-Windows-x64` 아티팩트에는 portable ZIP과 `SHA256SUMS.txt`가 들어 있습니다.

검토용 빌드도 전체 테스트, 실제 패키지 GUI·CLI 실행, 업데이트 도우미 검사와 이전 안정 버전에서의 업데이트 호환성 검사를 통과해야 합니다. 다운로드한 ZIP은 체크섬과 버전 표식, 압축 무결성을 확인합니다.

이미 통과한 동일 코드의 검사는 반복하지 않습니다. 검증된 후보와 정식 태그 사이에 승인된 안내 문서만 바뀌었다면 **Promote verified Windows build** 수동 워크플로로 기존 실행 파일을 재사용합니다. 후보 실행·아티팩트 ID와 두 커밋을 고정하고, 문서 외 코드 변경이 있으면 승격을 거부합니다. 원본 아티팩트의 전송 무결성을 확인한 뒤 README·CHANGELOG만 정식 태그의 내용으로 바꾸고, 나머지 패키지 파일이 동일한지 확인해 체크섬을 다시 만듭니다. 전체 테스트·컴파일·실행·업데이트 검사는 재수행하지 않습니다.

승격 워크플로는 파일을 기존 초안 릴리스에만 올립니다. 최종 배포 파일과 태그를 확인한 뒤 초안을 정식 릴리스로 공개하고 최신 버전으로 지정합니다. 프로그램 코드·의존성·빌드 설정이 바뀌면 기존 검증을 재사용할 수 없으므로 변경에 필요한 검사를 수행합니다.

검토용 파일을 먼저 제공하고, 사용자 지시에 따라 릴리스 게시를 진행합니다. 별도 게시 지시 없이 시험용 빌드 요청만 받은 경우 태그와 공개 릴리스는 만들지 않습니다. 게시 시에는 검증한 코드의 `vX.Y.Z` 태그를 만들고, 새 검증이 필요한 빌드 또는 위의 검증된 후보 승격으로 ZIP·체크섬을 준비한 뒤 공개합니다.

새 버전은 `folder_organizer/__init__.py`, `pyproject.toml`, `version.json`을 함께 변경합니다. `scripts/windows_upgrade_compatibility.py`의 이전 버전도 현재 공개 안정 버전으로 맞춥니다. 검토 중인 버전의 README에는 공개 안정 버전 다운로드와 검토용 빌드를 구분합니다.
