# 조회·분석 성능과 검사 범위

파일 수만으로 모든 작업의 시간을 설명할 수는 없습니다. 목록 조회는 파일·폴더를 방문하는 비용이 들고, 중복 검사는 실제 파일 바이트를 읽어야 하며, 화면 정렬에는 비교 비용이 듭니다. 이 문서는 어느 부분을 줄였는지와 재현 가능한 측정 범위를 구분합니다.

v0.7.0 Python·Rust의 같은 입력 Windows CLI 5회 교대 측정은 [실제 배포 결과](RELEASE_RESULTS_0.7.0.md)와 [원시 자료](EDITIONS_BENCHMARK_0.7.0.json)를 참고하세요. 아래 과거 버전의 Linux 측정과 구분하며 실제 NAS·콜드 캐시 성능은 주장하지 않습니다. v0.7.0 Rust의 내용 후보는 파일당 최대 64개 키를 사용하고 키·posting·후보·전체 비교 수를 제한합니다.

## 무엇이 달라졌나요?

- 폴더 탐색은 디렉터리 전체 목록을 정렬용으로 먼저 만들지 않고 순차 조회합니다. GUI는 코어의 마지막 정렬도 생략하고 화면 정렬을 따로 수행합니다. 기본 `scan_folder()` 정렬 동작은 기존 호출과의 호환을 위해 유지합니다.
- 상세 진행 이벤트를 파일마다 모두 만들지 않습니다. 처음 몇 항목, 일정 파일 수·시간 간격, 마지막 정확한 결과를 전달합니다. 발견 파일 수와 종료 상태를 유지하면서 GUI로 보내는 일을 줄입니다.
- 목록의 이름을 읽거나 정렬할 때 필요 없는 용량·두 날짜를 매번 문자열로 바꾸지 않습니다. 검색·문자열 정렬 키는 목록 생성 때 한 번 준비하고, 날짜·용량 표시값은 제한된 캐시를 사용합니다.
- 큰 목록의 유사 비교는 전체 파일을 방문해 후보 인덱스를 만들고 제한된 직접 비교를 수행합니다. 앞쪽 파일의 모든 조합에 비교 한도를 소모하는 문제를 줄입니다. **후보 방식은 모든 유사 쌍을 찾는다는 보장이 없습니다.**
- 완전 중복은 크기·전체 SHA-256·실제 바이트 검증을 유지합니다. 유사 후보나 캐시만으로 같은 파일이라고 판정하지 않습니다.

## 처리 비용의 의미

`n`은 검사하는 파일·폴더 항목 수, `B`는 읽어야 하는 파일 바이트, `P`는 경로·이름 문자열의 전체 길이입니다. 제한된 개수와 길이를 상수로 보는 일반적인 설명이며 실제 저장 장치·디렉터리 구조·파일 형식에 따라 시간은 달라집니다.

| 단계 | 비용과 한계 |
| --- | --- |
| 정렬 없는 폴더 탐색 | 항목을 한 번씩 방문하는 `O(n + P)` 작업. Windows에서는 안정적인 파일 ID를 위해 추가 경로 정보를 확인합니다. |
| 용량·정리 요약 | 파일 내용을 열지 않는 한 번의 메타데이터 집계. 큰 파일 상위 `L`개는 `O(n log L)`, `L`은 최대 100으로 제한합니다. |
| GUI 목록 준비·정렬 | 검색·정렬 키 준비는 문자열 전체 길이에 비례합니다. 키 조회는 일정 비용이며 실제 화면 정렬은 `O(n log n)` 비교를 수행할 수 있습니다. |
| 완전 중복 | 크기별 분류와 샘플로 다른 파일을 먼저 제외합니다. 필요한 전체 해시·바이트 검증에는 `B`에 비례하는 읽기가 필요하고, 경로 순서가 정렬되어 있지 않으면 `O(n log n)` 정렬도 수행합니다. |
| 빠른 유사 후보 생성 | 파일당 최대 31개 인덱스 키, 키당 최대 32개 보관 항목, 파일당 기본 최대 32개 후보를 사용합니다. 고정 한도에서 후보 생성 작업량은 `n`에 비례하도록 제한합니다. 콘텐츠 특징 추출·정확 중복 검사·최종 점수 계산 비용은 별도입니다. |
| 전체 쌍 유사 비교 | 같은 비교 종류 안에서 모든 조합은 최악 `O(n²)`입니다. 기본 25,000쌍을 넘으면 미검사 범위를 표시합니다. |

정확한 중복 검사에서도 해시 충돌을 가정해 실제 바이트로 다시 나누는 방어 경로는 최악의 조합 비교가 생길 수 있습니다. 따라서 모든 입력에 대한 전체 처리 시간이 `O(n)` 이하라고 보장하지 않습니다. 손실 없는 내용 검증을 생략해 속도를 만드는 방식은 사용하지 않습니다.

빠른 후보 인덱스의 키는 최대 65,536개를 유지하고 오래된 키를 교체합니다. 전역 비교 한도에 후보가 다 들어가지 않으면 전체 후보 흐름에서 고정된 방식으로 표본을 선택합니다. 뒤쪽 파일도 후보 탐색에 참여하지만, 키 교체·파일당 후보 한도·전역 한도 때문에 유사 쌍을 놓칠 수 있습니다. 결과의 **검색 방식·비교한 쌍·한도·경고**를 함께 확인하세요.

## 재현 방법

프로젝트 의존성을 설치한 저장소에서 실행합니다. 임시 합성 파일만 사용하며 개인 폴더를 변경하지 않습니다. 과거 소스는 `git show`로 별도 Python 모듈에 읽고 체크아웃이나 작업 트리를 바꾸지 않습니다.

```sh
python scripts/benchmark_analysis.py --suite scaling --counts 1000 2000 --repeats 3 --compare-revision 585d9f1
QT_QPA_PLATFORM=offscreen python scripts/benchmark_analysis.py --suite gui-keys --counts 1000 2000 --repeats 3 --compare-revision 585d9f1
python scripts/benchmark_analysis.py --count 64 --size 2097152 --repeats 3
python scripts/benchmark_analysis.py --count 64 --size 2097152 --repeats 3 --revision 585d9f1
```

`585d9f1`은 v0.4.0 기준 커밋입니다. 시간은 3회 중앙값입니다. 파일 생성 시간은 제외하며 OS 페이지 캐시가 따뜻할 수 있습니다. 같은 클라우드 실행 환경의 다른 작업도 시간에 영향을 줄 수 있습니다. 바이트 계수는 코드가 요청한 읽기 양이며 실제 디스크 트래픽이 아닙니다. `metadata_reads`는 명시적으로 요청한 메타데이터 조회 수이며, 캐시를 포함하는 운영체제 시스템 호출 수를 뜻하지 않습니다.

### 이미 검증한 중복 결과의 재사용

전용 버튼은 기존 프로세스가 인증한 해시·파일 식별자·변경 시각을 사용해 내부 실행 계획을 만들며, 별도의 미리보기 화면·추가 확인·전체 재분석 없이 delete_files로 원자 이동합니다. 최초 완전 중복 검사의 SHA-256·바이트 증거는 유지합니다.

| 중복 그룹 수 / 파일당 1 MiB | 내부 계획 준비 이전 → 이후 | 전체 지문 계산 이전 → 이후 | 지문 입력 바이트 이전 → 이후 |
|---|---:|---:|---:|
| 4 | 31.124 → 2.539 ms | 24 → 0회 | 24 MiB → 0 B |
| 8 | 78.589 → 4.353 ms | 48 → 0회 | 48 MiB → 0 B |

이 표는 최초 검사 이후 내부 계획 준비만 측정합니다. 실제 이동·네트워크 지연·서명된 작업 기록의 동기 저장 비용은 포함하지 않습니다. 파일 변경 작업의 단계별 체크포인트 저장에는 별도 비용이 있으므로 대량 이동 전체가 O(n)이라고 주장하지 않습니다.

```sh
python scripts/benchmark_analysis.py --suite duplicate-preview --counts 4 8 --size 1048576 --repeats 3 --compare-revision 585d9f1
```

## 복원 압축의 적용 범위

복원 메타데이터에는 원래 경로·보관 위치·해시·작업 상태가 들어갑니다. 파일 내용을 담은 원본·보호 사본도 함께 있어야 복원할 수 있습니다. 압축 메타데이터는 손실된 바이트를 만들어내는 방식이 아닙니다.

완료 시점의 기록만 gzip 수준 1로 압축합니다. 작은 기록은 기존 방식을 사용하고, 원본 기록 8 MiB·압축 기록 2 MiB 한도, 압축 CPU 작업의 250 ms 기준과 10% 이상 절감 조건을 적용합니다. 이 시간 기준은 파일 읽기·인증·디스크 쓰기 전체의 응답 시간 보장이 아닙니다. 압축이 적합하지 않거나 실패하면 기존 서명된 기록과 보관 파일을 유지합니다. 압축 복원 정보와 기존 체크포인트를 함께 보관하므로 압축 메타데이터가 전체 보관 용량을 줄인다고 주장하지 않습니다.

실제 원본 보관 데이터의 용량 최적화는 사용자가 작업 기록에서 별도로 요청합니다. 전체 바이트를 복원할 수 있는 보관 데이터를 유지하면서 압축·동일 청크 공유를 적용하고, 효과가 없거나 안전하게 완료할 수 없으면 원래 보관 파일을 유지합니다. 모든 파일을 항상 더 작게 만들거나 전역 최소 용량을 보장하지 않습니다.


### 실제 보관 데이터 코덱 확인

```sh
python scripts/benchmark_analysis.py --suite recovery-payload --sizes 1048576 2097152 --repeats 3
```

임시 원본을 인코딩·검증한 후 테스트용 입력을 제거하고 전체 SHA-256이 같은 파일을 독립적으로 복원했습니다. 이 표는 파일 내용 객체와 직렬화한 참조 크기이며 전체 작업 기록·파일시스템 블록·디렉터리 비용을 포함하지 않습니다.

| 합성 입력 | 실제 보관 객체 | 참조 정보 | 결과 |
|---|---:|---:|---|
| 반복 텍스트 · 파일당 1 MiB | 7,209 B | 750 B | 검증된 데이터만으로 복원 |
| 같은 고엔트로피 파일 2개 · 파일당 1 MiB | 1,048,576 B | 1,503 B | 검증된 데이터만으로 복원 |
| 고유 고엔트로피 원본 · 파일당 1 MiB | 0 B | 0 B | 이득 부족으로 기존 원본 유지 |
| 반복 텍스트 · 파일당 2 MiB | 7,209 B | 960 B | 검증된 데이터만으로 복원 |
| 같은 고엔트로피 파일 2개 · 파일당 2 MiB | 1,048,576 B | 1,939 B | 검증된 데이터만으로 복원 |
| 고유 고엔트로피 원본 · 파일당 2 MiB | 0 B | 0 B | 이득 부족으로 기존 원본 유지 |

이미 압축된 서로 다른 파일이 늘 작아지는 것은 아닙니다. 같은 조각은 공유하고 압축 효과가 없거나 안전하게 완료할 수 없는 항목은 원래 보관 방식을 유지합니다.
